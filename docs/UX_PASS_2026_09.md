# UX pass, September 2026

What changed after the first Vercel deploy, and why each decision was made the
way it was. Written so you can re-read it in three months and understand the
reasoning, not just the diff.

Scope was set from a list of things you noticed on the deployed site: problems
had no numbers, there was no light mode, playlists were unreachable, and the
navbar search did nothing. While tracing those four, a handful of smaller
defects turned up in the same code paths and were fixed alongside them.

Two things are deliberately **not** in this pass: the profile page redesign and
the broader visual overhaul. Both are waiting on your reference pictures.

---

## 1. Problem numbers

**Problem.** `Problem` had no human-facing identifier. Every list showed a bare
title, and the profile's solved list showed a truncated UUID, which is
meaningless to a user.

**Decision.** Added `number Int @unique @default(autoincrement())`.

Numbers are assigned by the database sequence when a problem is created, not
typed in by an admin. The alternative, letting the admin enter a number to
mirror LeetCode's real numbering, was rejected: it is manual work on every
problem, it needs its own uniqueness handling in the form, and there is no
reason CodeBounty's numbering has to agree with anyone else's.

The uuid `id` stays the routing and relation key. The number is presentation
only. That keeps the number safe to change later if you ever want to renumber,
because nothing points at it.

**Migration.** `prisma/migrations/20260909130000_add_problem_number`.

It does not use a plain `SERIAL` column, even though that is what Prisma would
generate. `SERIAL` numbers existing rows in whatever order Postgres happens to
walk the table, which is arbitrary. Instead the migration adds the column as
nullable, backfills it with `ROW_NUMBER()` ordered by `createdAt`, then creates
the sequence starting after the highest backfilled value and attaches it as the
default. The end state is byte-for-byte what `SERIAL` produces, so Prisma sees
no drift; only the backfill order differs.

**Follow-on changes.**

- `getAllProblems` now orders by `number` ascending instead of `createdAt`
  descending. A catalogue that reorders itself as problems are added is
  disorienting, and users refer to problems by number.
- `getPatternBySlug` orders by difficulty then number.
- Search matches the number as well as the title, so typing `121` finds problem
  121. See `matchesQuery` in `modules/problems/components/problem-table.jsx`.

## 2. Light and dark mode

**Problem.** `next-themes` was installed and configured, and a `ModeToggle`
component already existed, but three things blocked it from working:

1. The toggle was never rendered anywhere.
2. `enableSystem` was `false` with `defaultTheme="dark"`.
3. `:root` in `globals.css` held the **dark** values, and `.dark` held an
   identical copy. Because `next-themes` applies the `dark` class to `<html>`
   for the dark theme, `:root` is by definition the light theme. Switching would
   have produced no visible change.

**Decision.** `:root` now holds a real light palette and `.dark` holds the
existing dark values. Token names are unchanged, so no component needed editing
to gain light mode.

The light accent is violet-600 (`#7C3AED`) rather than the dark theme's
violet-500. Violet-500 on white does not reach 4.5:1 contrast for text; violet-600
does. Similarly, success, error, and pending each step one shade darker in light
mode for the same reason.

The shadcn compatibility aliases (`--background`, `--card`, `--primary`, and so
on) now only ever point at our own tokens, in both blocks. Previously they were
duplicated with literal values in places, which is how the two blocks drifted.

**Clerk.** Clerk renders its own DOM and cannot read our CSS variables, so its
theme has to be passed in JavaScript. Previously only the sign-in and sign-up
pages set one, always to `dark`, which left the `UserButton` in the navbar on
Clerk's light default sitting on a dark navbar. New file
`components/providers/clerk-theme-provider.jsx` wraps `ClerkProvider` and feeds
it `baseTheme` from `resolvedTheme`. This required flipping the provider nesting
in `app/layout.js`: `ThemeProvider` is now the outer one, because the Clerk
wrapper is a client component that calls `useTheme`.

`clerk-appearance.js` kept its element classNames, which already use our tokens
and therefore work in both themes, and lost its hardcoded `baseTheme` and colour
hexes.

**Monaco.** The problem page imported `useTheme` and never used it, then
hardcoded `theme="vs-dark"`. It now follows `resolvedTheme`.

The admin create-problem editor deliberately stays dark. Its surrounding chrome
is a fixed dark shell (`bg-zinc-950` with a fake title bar), so a light editor
inside it would look broken. If that shell is ever tokenised, the editor should
follow the theme too.

**Toggle behaviour.** `ModeToggle` reads `resolvedTheme`, not `theme`. With
`enableSystem` on, `theme` can be the string `"system"`, and toggling away from
that would always land on dark regardless of what the user is currently seeing.
It also renders a same-sized empty box before mount instead of `null`, because
returning `null` made the whole navbar shift on hydration.

**Body classes.** `app/layout.js` had `bg-base text-primary` on `<body>`.
Neither is what it looks like: there is no `bg-base` token (ours is
`bg-bg-base`), and `text-primary` resolves to `--color-primary`, which is the
**accent** colour, so the default body text colour was violet. Both were
removed; the `@layer base` rule already paints the body correctly.

## 3. Navbar search

**Problem.** The Ctrl+K command menu listed three hardcoded navigation links and
nothing else. It never searched problems, which is what its placeholder text
promised.

**Decision.** On first open it calls the existing `getAllProblems` server action
once, caches the result in component state, and lets `cmdk` filter client-side.
Each item's `value` is `"<number> <title>"`, so both are searchable.

Why not a server-side search endpoint: it would need a new action, debouncing, a
loading state per keystroke, and cursor handling, to solve a problem the app does
not have yet. `getAllProblems` already returns exactly the list-safe fields and
is already cached per request. There is a `ponytail:` comment at the fetch
marking the ceiling: move to a server query past a few hundred problems.

The static navigation entries stay, as a second group below the results.

## 4. Playlists

**Problem.** This was worse than "not clickable". `create-playlist.jsx` and
`add-to-playlist.jsx` existed but were imported by nothing, so there was no way
to create a playlist or add a problem to one. There was no playlist page and no
detail route. The profile rendered playlist cards that linked nowhere.

**Decision.** Built the whole flow, modelled on the reference screenshot.

**Server actions replace the API routes.** `app/api/playlists/` and
`app/api/playlists/add-problem/` are deleted. Everything now lives in
`modules/playlists/actions/index.js`. Reasons:

- The old routes duplicated the same twelve lines of auth boilerplate in each
  handler. The actions use the shared `getDbUser` helper, which is wrapped in
  React `cache()` and so does not re-query per call within a request.
- Client components had to hand-roll `fetch`, parse the envelope, and handle
  non-JSON failures. Server actions remove that layer entirely.
- Cache invalidation becomes `revalidatePath` at the mutation site rather than
  manual refetching in the component.

**Ownership is re-checked on every action.** Playlists are private, so an id
handed in by the client is never trusted. Reads use `findFirst` with both `id`
and `userId`, and `deletePlaylist` uses `deleteMany` scoped by `userId` rather
than `delete` by id, which would otherwise let one user delete another's list.
A playlist that is not yours returns "not found", which does not confirm it
exists.

**Two Prisma unique-constraint violations are treated as user outcomes, not
errors.** Creating a playlist whose name you already used returns "You already
have a playlist with that name" rather than a generic failure. Adding a problem
that is already in the list returns success with `alreadyPresent: true`, because
from the user's point of view the desired state was already true.

**Routes.**

| Path | What it is |
|---|---|
| `app/(root)/playlists/layout.jsx` | The "My Lists" rail plus the content pane |
| `app/(root)/playlists/page.jsx` | Index: cards, or the empty state with a create button |
| `app/(root)/playlists/[id]/page.jsx` | Detail: header, progress, difficulty breakdown, problem list |

The sidebar lives in the layout rather than in each page, so moving between
lists re-renders only the detail pane and the rail keeps its scroll position.

**Progress ring.** `modules/playlists/components/progress-ring.jsx` is a plain
SVG arc, about forty lines. Recharts is already in the bundle and has a
`RadialBarChart` that would do it, but a single arc does not need a chart
library, an axis system, or a responsive container.

**Practice button.** Links to the first *unsolved* problem in the list, falling
back to the first problem. Resuming is more useful than restarting.

**Shared problem row.** `modules/problems/components/problem-row.jsx` is new. The
catalogue, the pattern detail page, and the playlist detail page all rendered
their own near-identical row markup, and they had already drifted: only the
catalogue showed patterns, only the catalogue was responsive. One component now
serves all three. It takes a `trailing` slot so a caller can hang a
list-specific control on it, which is how the playlist page gets its remove
button without the row knowing playlists exist.

**Deletion is confirmed through `AlertDialog`**, not `window.confirm`, which the
app cannot style and which blocks the page.

## 5. Smaller fixes found along the way

**`react-hook-form` was missing from `package.json`.** It is imported by
`create-problem-form.jsx` and was only resolving because npm had hoisted it as a
transitive dependency of `@hookform/resolvers`. A clean install on Vercel could
have dropped it and broken the build. Now declared explicitly at `^7.84.0`.

**Search results could render invisible.** Catalogue rows animated in with
`whileInView` and `viewport={{ once: true }}`. When filtering replaced the list,
rows that had never been observed stayed at `opacity: 0`. The per-row entrance
animation is simply gone. A staggered fade on a data-dense list is not worth a
bug that hides search results.

**The solved-problems list showed UUID fragments.** `getCurrentUserData` used
`solvedProblems: true`, which returns the join rows only, so the component had
nothing to display but `problemId.slice(0, 8)` under a hardcoded heading reading
"Problem Solved". The query now includes the related problem, and the list shows
number, title, difficulty, and date, each linking to the problem.

That same query now includes the problem on submissions, orders both newest
first, caps submissions at 50, and includes a problem count on playlists.
Previously it fetched every submission a user had ever made with no limit.

**No mobile navigation.** Nav links were `hidden md:flex` with no replacement
below that breakpoint, so on a phone the only reachable pages were the logo link
and whatever the search offered. Added a `Sheet` menu. The link list is defined
once in `NAV_LINKS` and rendered by both the desktop bar and the sheet.

**No active-page indicator.** The navbar now highlights the current section.
`isActive` matches the exact path or a `/`-prefixed child, so `/problems` does
not light up while you are on `/problem/abc`.

**Build log noise.** `/` and `/problems` read the Clerk session, so they can
never be prerendered, but they did not say so and every build logged
`DYNAMIC_SERVER_USAGE` errors for them. Both now declare
`export const dynamic = "force-dynamic"`.

**Toaster.** `app/layout.js` imported `Toaster` straight from `sonner`, bypassing
`components/ui/sonner.jsx`, which is the wrapper that feeds it the current theme
and the app's icons. Now imports the wrapper.

## 6. Second sweep

A closer read of the profile, dashboard, and submission components turned up
four more problems.

**The profile page crashed for unnamed users.** `user-info.jsx` read
`userData.firstName[0]` and `userData.lastName[0]` for the avatar initials. Both
fields are optional in the schema and Clerk does not require them, so any user
who signed up without a name got a `TypeError` and a blank profile. Name and
initials are now assembled from whichever parts exist, falling back to the email
initial.

**Invented statistics were shown as real.** The submission detail view claimed
every submission "Beats 84.2% of users" on runtime and "62.8%" on memory. Both
were string literals, identical for every submission ever made. Below them sat a
"Runtime Distribution" histogram generated from a bell curve in JavaScript,
unrelated to any real data. All three are deleted rather than relabelled. A
number a user cannot trust is worse than no number, and we do not yet record the
cross-user timings needed to compute a real percentile.

Removing the histogram also removed the last `recharts` import from that file,
along with its hardcoded dark tooltip colours.

**The dashboard's streak and solved split were mocked.** The streak was the
literal `5` whenever the user had any submission at all, with a comment saying
so. The difficulty donut was fixed at 45 easy, 30 medium, 10 hard for everybody.
Both are now computed:

- Streak counts consecutive days back from today on which the user submitted
  anything. It tolerates today having no submission yet and starts from
  yesterday, otherwise every user's streak would read zero each morning until
  they submitted.
- The donut tallies the real difficulties of solved problems, and empty slices
  are dropped so a user with no hard solves does not get a zero-width wedge.

The dashboard's submission rows also showed `Problem #a1b2c3`, a slice of the
uuid. They now show the number and title, linked to the problem. The row's click
handler expands the row, so the link calls `stopPropagation` to avoid doing both.

That table had the same `whileInView` / `once: true` bug as the catalogue:
filtering the list left newly matching rows invisible. Changed to `animate`.

**The submission list could not tell rows apart on the profile.** Every row
showed status, language, runtime, memory, and date, but never which problem it
belonged to. The component now shows a Problem column when the data includes
one, which is true on the profile and false on a problem page, where naming the
same problem on every row would be noise.

## Deploying this

The migration must be applied before the new code runs, or every query
selecting `number` will fail.

```bash
npx prisma migrate deploy
```

It is additive and backfills in place, so it is safe on the live database and
does not need downtime. There is no rollback path that preserves the assigned
numbers, so take a Neon branch or snapshot first if you want one.

## 7. The whole site was behind the login wall

`proxy.js` protected every route and exempted only `/sign-in` and `/sign-up`.
That included `/`. A signed-out visitor to the deployed site was redirected to
sign-in before ever seeing the landing page, which meant the marketing copy, the
feature section, and the navbar's entire signed-out branch, its Log in and Sign
Up buttons, were unreachable code.

Confirmed against the dev server: `GET /` returned `307` to
`/sign-in?redirect_url=...`.

Inverted the rule. It now protects a named list rather than protecting
everything and carving out exceptions:

| Public | Protected |
|---|---|
| `/`, `/problems`, `/patterns`, `/patterns/[slug]`, `/problem/[id]` | `/profile`, `/playlists`, `/dashboard`, `/create-problem`, `/api/create-problem` |

Browsing is public, anything tied to a specific user is not. Reading a problem
stays public deliberately: it is the natural funnel into signing up, and the
page's own server actions check the session before they run or record anything,
so a signed-out visitor can read but not submit.

An allowlist of protected routes is also the safer shape to maintain. Under the
old rule, adding a public page meant remembering to exempt it, and forgetting
silently locked it.

## 8. Profile page rebuild

Rebuilt around the LeetCode profile layout you asked for: a sticky left rail
carrying identity and progress, and a scrolling right column carrying activity.

**What maps across, and what does not.**

| LeetCode card | CodeBounty |
|---|---|
| Identity, rank | Identity. No rank, we have no ranking system |
| Languages solved | Built from `Submission.language` |
| Skills, grouped by tag | Patterns, with per-pattern progress |
| Solved donut plus difficulty bars | Same |
| Submission heatmap, active days, max streak | Same |
| Recent AC | Same |
| Contest rating, badges, reputation, community stats | Dropped. No data behind any of them |

Rather than inventing numbers to fill those last cards, they are gone. That is
the same judgement as deleting the fake "Beats 84.2%" figures in section 6.

**Languages counts distinct problems, not submissions.** Ten attempts at one
problem in Python is one problem solved in Python, not ten. It also counts only
accepted submissions.

**Skills became Patterns.** LeetCode groups this card by tag under Advanced,
Intermediate, and Fundamental. Patterns are a better fit for us: they are
already the app's primary browse axis, they already carry a learning order, and
the per-pattern tally helper `tallyByPattern` already existed. Each row links to
that pattern's page.

**One query, not six.** `getProfileData` fetches the user with submissions,
solved problems, and playlists, then runs the catalogue totals and the pattern
list in parallel. The totals are needed because progress is shown as "solved out
of total", which means nothing without the denominator.

`getCurrentUserData` is kept, because the dashboard still imports it.

**The heatmap moved and grew up.** It was defined inside `dashboard-client.jsx`,
the only place it existed. It is now
`modules/profile/components/activity-heatmap.jsx` and shared. Three changes came
with the move:

- Laid out in week columns with month labels, like GitHub and LeetCode, instead
  of one long scrolling row.
- Four fixed intensity buckets instead of scaling opacity against the busiest
  day, so a quiet week does not make one submission look like a heavy day.
- Reports total submissions, active days, and max streak above the grid. Max
  streak is computed across the whole history, not just the drawn window.

**Four components deleted.** `profile-stats.jsx`, `solved-problems.jsx`,
`user-info.jsx`, and `playlist-section.jsx` are gone, replaced by
`profile-identity`, `solved-summary`, `language-stats`, `pattern-skills`,
`activity-heatmap`, and `profile-activity`. The old ones carried hardcoded blue,
green, purple, and amber card backgrounds that ignored the design tokens and
were the main reason the page looked pasted together.

**The lists are tabs now**, Recent AC, Solved, Submissions, and Playlists, rather
than four stacked cards. The old page put a full submission history and a full
solved list on screen at once, which pushed the playlists below two screens of
scrolling.

`ProgressRing` gained an `arc` prop. The playlist page keeps the three-quarter
dial from your reference; the profile passes `1` for a closed ring.

## 9. Saving a problem, and adding problems from inside a playlist

Two gaps in the playlist flow, both raised after the first pass:

1. No way to save a problem from a list. The only Save control was on the
   problem page itself, so building a list meant opening every problem.
2. No way to add problems from inside a playlist. You could only push problems
   into a list from elsewhere, never pull them in.

**The save bookmark.** Every catalogue row now ends with a bookmark, on
`/problems`, on a pattern page, and inside a playlist. Clicking opens a picker
rather than silently favouriting: the destination stays visible, every list is
one tap away, and a new list can be typed in without leaving the row. Creating a
list from that field means "put this problem in it", so it creates and adds in
one action.

A bookmark, not a star. The star is LeetCode's mark and reads as "favourite",
which is narrower than what this control does, and copying it makes the app look
like a clone rather than its own thing. A bookmark reads as "save this
somewhere", which is exactly the picker's behaviour.

**Filled means saved to any list, not just Favorites.** A bookmark that stayed
hollow for a problem the user had filed under their own "DP drills" would be
lying about the thing it exists to report. `getSavedProblemIds` returns a
distinct set of problem ids across all of the user's playlists.

**Favorites is created on first use, not at sign-up.** No `isFavorites` column,
no flag, no migration, and no empty list following around users who never star
anything. It is an ordinary playlist named `Favorites`, so it renames, deletes,
and lists like any other. The trade-off is that the name is the identifier: a
user who renames it gets a fresh Favorites next time they star something. That
is acceptable for a list the user chose to rename, and the alternative is a
schema column earning its keep only in this one place.

**One toggle action, not add plus remove.** `toggleProblemInPlaylist` adds when
absent and removes when present, which is what a checklist row needs. Called
with no playlist id it targets Favorites, creating it if this is the user's
first star. The older `addProblemToPlaylist` stays for the problem page's Save
dialog, where "add" really is the only intent.

**Bookmarks cost one query per page, not one per row.** `getSavedProblemIds`
returns the membership as a flat list, which the page turns into a Set. Each row
then reads its own state from memory. The full per-playlist membership loads only
when a bookmark is actually clicked.

After a toggle the control re-derives its fill from the refreshed rows, since
removing a problem from one list does not un-save it if another list still holds
it. It updates locally rather than waiting for the server round trip, so it
responds instantly.

**Add problems dialog.** The playlist header and the empty state both open a
searchable catalogue where tapping a row adds or removes it. It reuses the same
`matchesQuery` helper as the catalogue search, so searching by number works
here too. The dialog deliberately stays open after each add, because adding
several problems in a row is the normal case, not the exception.

**Mobile rows were restructured.** The control was first placed absolutely at
the row's top right, where it landed on top of the difficulty badge. Title, badge,
and controls now share one flex row, with only the title being a link.
